# 维护形式化验证

形式化检查证明的是它所描述的东西的性质。代码变了、验证没变，检查可能照样通过，描述的却是已经不存在的代码——这种通过最危险，因为它看起来像证明。项目本地的 verify skill 处理用它的 agent 自己做的改动；这一轮处理绕过它的改动：合并、没用 skill 的编辑、许多 commit 累积的漂移。

## 结局

每个检查取一个，并说明是哪一个：

- **同步**：同步点之后没有改动影响它描述的东西，检查通过。
- **已更新**：代码变了，验证已改成描述新代码，检查通过。
- **bug**：验证描述的是当前代码，代码违反了性质。这是代码的问题，不是漂移。
- **受阻**：没法让检查跟上或跑不起来，写清原因。

一个检查可以既是「已更新」又是「bug」：更新后验证重新对上代码，然后性质在它上面失败。

## 改动范围

只改验证本身：模型、harness、性质文件和 verify skill。用户没要求就不改产品代码。性质在当前代码上失败时，不削弱性质或模型去让它通过，报告失败。

## 一轮维护

1. **找到检查**：verify skill 没有固定名字，按它做的事找——跑模型检查器、证明器或其它验证器去验具名代码的项目 skill。逐个读（或只读用户点名的那个），为每个检查收集：性质、覆盖的代码、界和假设、运行命令、同步点。一个都没有，就停下改走 SKILL.md 的创建流程。skill 没记同步点，就用最后一次改验证文件的 commit，并说明这么做了。
2. **原样跑一次**：动手前每个检查先跑一次并记录。这时通过不说明代码正确，只说明旧描述还成立；这时失败可能是漂移也可能是 bug，到第 5 步再判。
3. **读覆盖代码的每处改动**：从同步点 diff 到当前 commit，读每条 commit 信息。也找挪走的代码：被重命名、拆分或移到别的文件的被覆盖函数，仍是被覆盖代码；也找碰到检查所守状态的新代码，比如写同一批字段的新函数。每处改动归为一类：
   - **无影响**：不改变验证描述的任何东西（格式、注释、验证不覆盖的路径）。对着模型或 harness 判断，不对着 commit 信息。
   - **验证不再描述代码**：原来不可分的一步变成两步、加了或删了分支、检查挪了位置、新路径能到达被守护的状态、某个值的范围变了。模型或 harness 必须改。
   - **承诺被有意改了**：改动改变了代码的承诺，且改动里有证据说明这是有意的（文档注释、测试、changelog、commit 信息）。性质必须改，并引用证据。
   - **承诺可能被破坏**：代码变了，没有证据说承诺变了。之后的失败当作 bug 候选。
4. **从代码出发更新，不从结果出发**：让每个改过的部分重新指向评审者能打开的代码，代码里不可分的一步在验证里仍是一步。重跑前先照代码写好更新，不要照着「怎样能通过」去塑造它。只对有意改变的承诺改性质，写下旧措辞、新措辞和证据。界保持不变，除非改动让它不再成立；不得不缩小界时在报告里说明。
5. **重跑并判每个结果**：
   - **通过**：更新后的描述可能已经失去失败的能力。按性质防的那种方式弄坏新代码（删掉新加的检查、调换新步骤），确认检查抓得到，再撤掉。
   - **失败**：在真实代码上逐步回放反例。某一步在代码里不可能发生，就是验证错了，修验证并说明错在哪。每一步都可能发生，就是 bug：指出引入它的 commit，把反例讲成代码里的一串步骤，用一句话说危害。有便宜的测试或复现能在真实代码上显示这个 bug，就作为证据放进报告，不提交进产品代码。
6. **更新 verify skill**：更新每个检查覆盖的代码、命令、界、假设和同步点，同步点设为你检查过的 commit；受阻的检查不挪同步点，并在报告里说明。然后像下一个 agent 那样照 skill 跑一遍，确认步骤仍然跑得通。

## 报告

逐个检查说明：

- 结局，以及读过的 commit；
- 验证改了什么、为什么：代码换了形状，或承诺被有意改了（附证据）；
- 重跑结果，以及用来证明更新后的检查仍会失败的那次破坏；
- 每个 bug 用大白话讲反例步骤、危害和引入它的 commit；
- 验证仍不覆盖什么，包括本该覆盖却没覆盖的新代码。

明确说哪些失败是验证漂移、哪些是代码 bug；更新前通过、更新后失败的检查，要说明旧的通过建立在过期描述上。验证的更新单独成一个变更，和任何产品修复分开。
