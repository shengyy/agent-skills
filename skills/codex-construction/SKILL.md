# codex-construction — 轻量派工编排

核心哲学：新一代模型（GPT‑5.6+/Claude 5+）能力过剩，编排的价值在**分工、边界、验收**，
不在过程管控。不替 codex 写码，不给实现细节，不搭沙箱管道；给合同、给自主权、验收结果。

## 分工

- **主代理**（任意模型，不锁死）：产品/架构方案与施工合同、拆批、派工、监控、分批验收、终审。
- **Codex**：一批之内全自主——读合同、实现、跑门禁、分阶段 commit、写验收包。
- 主代理不要中途接管施工，codex 不要反向出产品级裁决；两边都越界就乱。

**为什么必须有监工**：codex 独立干活的系统性偏差是**过度工程**（防御层、状态机、
分类学自发膨胀）；放权施工 + 主代理监工恰好互补。监工只盯三件事，不管过程：

1. **方案裁决在先**——复杂度要在合同定稿时杀掉，施工中再拦成本翻倍；
2. **分批验收盯复杂度漂移**——验收包里新出现的合同外机制按负收益默认拒收，
   要求论证真实威胁模型才保留；
3. **BLOCKED 裁决**——codex 停下来问的点快裁快回，不让施工空转。

## 调用

```bash
codex exec -m gpt-5.6-sol -c model_reasoning_effort="<high|xhigh>" -s danger-full-access "$(cat PROMPT_FILE)"
```

- 模型：`gpt-5.6-sol`（2026-07 当前最优；模型换代只改这一处）。裸传简称会被服务端 400 拒。
- effort：`high` = 边界清楚的常规施工、定点修复、**收口核验轮**（验证指定修复落点的轻量复审）；
  `xhigh` = 架构级重构、资金/并发核心、**全面对抗审查轮**（跨模块因果链追踪型发现只在这一档稳定出现）。
  多视角审查并行开会话，墙钟时间只等最慢一路，别为省时间降全面审的档。
- `danger-full-access` 没有沙箱兜底：**一切边界靠 prompt 写明**（见模板第 5 条）。

## 启动（launch-only 原则）

```bash
nohup bash -c 'codex exec ... "$(cat PROMPT_FILE)"' > RUN.log 2>&1 & echo "pid=$!"
```

- prompt 先写文件再 `cat`，避免引号地狱；日志放任务专属 tmp 目录。
- 启动调用必须秒回：**同一次 Bash 里不得再带任何耗时前台命令**——外层超时按进程组
  SIGKILL，`nohup` 挡不住组杀，会把刚起的 codex 连带杀死且日志无收尾。
- 运行中的日志不要 truncate（`>` 重定向下会变稀疏文件，破坏完成检测）。

## 监控（三终态，不看 PID）

| 终态 | 判定 |
|---|---|
| 完成 | 日志出现 codex 收尾标记 `tokens used` |
| 崩溃 | 进程消失且无收尾标记 |
| 停滞 | 日志 mtime 静默 20–25 分钟 |

坑：不要直接 grep 自己定义的完成标记——codex 会**回显 prompt 原文**（内含标记文本），
必须先确认 `tokens used` 再解析其后的输出。

## Prompt 模板（五要素，轻量）

1. **现场**：仓库路径、分支、前序进度（已有 commit / 验收包位置）。
2. **合同**：指向方案/任务文档路径让 codex 自己通读；不要把方案正文塞进 prompt。
3. **范围**：本批做什么、明确不做什么（防提前施工后批内容）。
4. **硬规则**：只写真红线（如禁补丁/禁兼容/禁双轨/唯一事实源、源码规模上限、必须保留清单）。
   不写实现细节——细节约束越多，模型被迫选次级方案的概率越大。红线用具体动作边界表述
   （push/部署/生产库），不写「绝不改动任何状态」式抽象绝对句——那会把工具自身副作用
   （日志/缓存）也卡成越界，白烧一轮。
5. **边界与交付**：不 push、不碰生产态（部署/systemd/生产库）、只 stage 本任务文件；
   分阶段 commit + 验收包；完成时末尾单独一行打印约定标记（如 `STAGE N DONE` + commit hash）；
   遇合同矛盾或必须越权时写「待裁决」并打印 `BLOCKED: <原因>` 停在阶段边界。

**自主权条款（关键，必写）**：施工中发现的真实问题，允许 codex 在范围内自行根因修复并记入
验收包；只有推翻合同前提或触碰红线才 BLOCKED。这是发挥新模型能力的核心一条。

验收包最小骨架：目标 / 实际 diff 摘要 / 物理删除项 / 测试状态（含预期 RED）/ 未验证项。

## 批次编排

- 同一工作树 = **串行**；并行只允许各自独立 worktree 且文件集不相交。
- 一批 = 一个可独立验收的工作包；批间主代理验收后才放行下一批。
- 大工程默认三段：先立骨架（含 RED 测试）→ 重改动 → 机械收尾（拆分/清扫）。
- **树静默原则**：codex 施工中不要并行跑门禁、切分支或改同树文件。

## 改-审循环

- 审查用**全新 codex 会话**（独立性优先，不 resume 施工会话）；prompt 要求对抗式、
  按严重度分级、每条给复现路径；涉及数据/状态的审查喂只读副本接地，不连生产。
- 修复轮可续上下文：`codex exec resume --last -m <model> -c sandbox_mode="danger-full-access" "<prompt>"`。
  权限与施工轮完全一致（`-c sandbox_mode` 与 `-s` 是同一配置项的两种写法）；仅因 resume
  子命令未实现 `-s` 快捷别名（clap 拒收），才改用 `-c` 通用写法，不是降级进沙箱。
- 重大改动**按视角拆审**：正确性/回归、数据与状态安全、删除完整性（双轨残留）各起一个
  独立审查会话——一个通用审查会漏掉视角外的失败模式。
- 收口判据用 **until-dry**：连续两轮审查无阻断性新发现才算干净；一轮干净就停会漏长尾。
  "non-blocking" 留痕即可。
- **主代理必须抽验**：自己重跑关键门禁（lint/smoke），不全信日志里的 "passed" 字样；
  发现过换掉门禁项蒙混的先例。验收还要抽查关键不变量（安全链、被保护符号是否存活）。

**修复循环熔断（升级到方案层，不是加轮次）**：阻断性修复超过约 3 轮仍不收敛，或出现
振荡信号——修 A 破 B、同一区域反复出问题、原先干净的区域冒出新阻断——立即停止修复轮。
持续振荡说明错的不是实现而是方案/架构：主代理回到方案层重新裁决（缩小范围、改设计、
推倒该批重来，必要时找用户）。把「方案错了」当「还没修完」继续加轮，是这套流程最贵的浪费。
