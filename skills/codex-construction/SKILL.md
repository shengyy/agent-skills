# codex-construction — 写好简报，然后放手

把 Codex 当成一位顶尖工程师：告诉它为什么做、做成什么样、什么最重要、做到多好、要什么品味，实现交给它。主代理的功夫花在简报和验收上，不花在过程管控上。

## 分工

- **主代理**：吃透目标、写简报、拆批、定档、派工、验收、做产品裁决。
- **Codex**：一批之内的全部实现决策——读代码、设计、实现、跑门禁、分阶段 commit、写验收包。
- 互不越界：主代理不中途接管，做砸了带着反馈重派；Codex 不做产品裁决，遇到就 BLOCKED。

## 写简报

简报用自然段写，像给一位没参与前期讨论的资深同事交代任务。正文五段，结尾固定两段。

**正文五段**

1. **背景**：这是什么项目、为什么要做这件事、做成了对谁有什么价值、现在走到哪一步（仓库路径、分支、前序 commit、方案文档路径，让它自己通读）。动机讲清楚，很多你没写的约束它能自己推出来。
2. **交付**：最终交出的东西长什么样——哪些行为可以被验证、在什么数据或场景下成立、commit 怎么切。最终消息是验收包：目标 / diff 摘要 / 删除项 / 测试状态（含预期 RED）/ 未验证项与理由。
3. **重点**：这一批真正要紧的是什么、用户最在意什么、哪里最容易做错；也写明这批不做什么。重点只挑一两个，全都重要就等于没有重点。
4. **质量与资源**：定门槛，也给资源。门槛写成可感知的标准，例如「做到你愿意署名、拿给资深同事 review 也不心虚」；明确允许它花时间读代码、试错、反复迭代、自己跑门禁和压测。测试守住真正会坏的地方，可逆、低影响的改动不写镜像实现的测试。你知道的好工具、现成数据、同类实现和已知的坑放在这里，用「可以考虑」「我觉得 X 够用」的口吻给，它有更好的办法就用它的。
5. **风格与品味**：希望代码读起来像什么——像这个仓库原本就有的代码；能删就不加；不引入简报外的新抽象、配置项或兼容层；指一两个写得好的文件做参照。这一段决定交付物的气质，值得写具体。

**固定结尾**

- **红线**：只写不可逆的动作边界，用具体动作表述（push、部署、生产库、付费 API），不写抽象的绝对句，不写实现细节。没有就写「无」。
- **运行约定**：照抄下面这段，把 `N` 换成批号；监控和续接依赖它。

```text
这是无人值守的单轮会话，没有人会回答问题：遇到歧义按最合理、低风险的理解继续，并把判断写进验收包。不必先交计划或中途汇报，最终消息只要验收包。施工中发现的真实问题，在本批范围内从根因修掉并记录；只有推翻简报前提、需要产品裁决或要越过红线时才停下。
最终消息末尾单独一行：完成写 `STAGE N DONE <commit hash>`；需要裁决写 `BLOCKED[批N]: <原因>`，并停在最近的阶段边界。
```

不要求先出计划：`codex exec` 是单轮会话，要求先交计划它就会交完计划结束。

**派工前自检**：一位没参与讨论的顶尖工程师只读这份简报，能不能说出为什么做、做成什么样算好、什么最重要、什么样的代码算有品味？说不出来就补简报，别靠事后返工补。补不上的那段——通常是重点和品味——在用户心里，先问用户，别替用户编。

**示例**（运行约定照抄上文，此处省略）

```text
背景：shop-api 的订单导出每次全量拉库，大客户导出要 10 分钟，经常超时，客服每周都在帮客户手工拆单。这批把导出改成流式分页。方案在 docs/plans/export-streaming.md，先通读；上一批已在 feat/export 分支合入游标 API（a1b2c3d）。

交付：用 scripts/seed-large.ts 生成的 50 万单数据集上，导出 1 分钟内完成、进程内存平稳；旧的全量路径删除；按阶段 commit。

重点：用户最在意的是导出不再超时。CSV 的列和格式一个字节都不能变——财务有脚本在解析它。这批不碰导入功能。

质量与资源：做到你愿意署名为止。先花时间读懂现有的分页和鉴权代码再动手，自己跑门禁和压测，压测不达标就继续迭代。测试守住游标边界、空结果和中途断连。我觉得项目里已有的 pg-cursor 够用，你有更好的办法就用你的。

风格与品味：读起来像这个仓库原本就有的代码，src/export/invoice.ts 是写得不错的同类实现。能删就不加，不引入方案外的抽象、开关或兼容层。

红线：不 push、不部署、不连 .env 里的生产库。
```

## 档位

effort 用 `medium` / `high` / `xhigh` 三档，跟**简报留给 Codex 的判断空间**和**出错代价**走。质量门槛定得多高，档位就给多足。

- `medium`：简报已把「做什么」说透，Codex 只决定局部「怎么做」，做错了门禁或 diff 能抓住。常规施工默认档。
- `high`：要做设计、排查根因未知的问题、跨模块重改动、全批次审查，或 medium 没过的重派。
- `xhigh`：错了要回滚多批——架构定型、资金/并发/安全核心、最终态对抗审，或 high 重派仍失败的最后一轮。

用户点名档位或模型时按用户的。重派升一档，xhigh 仍不过就回方案层。审查档不低于被审批次的施工档。想省额度，就把简报写透、把批拆细，不压审查档。

## 启动

```bash
nohup bash -c 'exec codex exec -m gpt-6-astra -c model_reasoning_effort="medium" \
  --dangerously-bypass-approvals-and-sandbox -o LAST.md - < BRIEF_FILE' > RUN.log 2>&1 & echo "pid=$!"
```

- 模型名以本机 `~/.codex/config.toml` 为准；换名先用 `codex exec -m <名字> "打印 ok"` 探针，400 即无效。
- **简报走 stdin**（`- < FILE`）：放在 argv 会暴露到 `ps`，Codex 可能把自己的进程误认成另一个会话，转去监控而不开工。
- **`exec` 不能省**：有它 `$!` 才是 codex 本身，杀进程才杀得到 codex。
- `--dangerously-bypass-approvals-and-sandbox` 关掉沙箱和审批，exec 和 resume 都收；没有兜底，边界只靠简报红线。
- `-o LAST.md` 把最终消息单独落盘，每批独立命名，启动前不得已存在。
- 启动调用只负责后台派工并立即返回；外层工具超时会按进程组 SIGKILL，`nohup` 挡不住。
- 启动后看 `RUN.log` 头部：记下 `session id:` 供续接，核对 `reasoning effort:` 是所选档。

## 监控

进程还在就是在跑，`kill -0 <pid>` 判活即可，不解析日志。进程退出后看 `LAST.md`：

| 终态 | 判定 | 处置 |
|---|---|---|
| 完成 | `LAST.md` 末行 `STAGE N DONE` | 验收 |
| 待裁决 | `LAST.md` 末行 `BLOCKED[批N]:` | 裁决后 resume |
| 无交付 | 有 `LAST.md`，没有标记 | 读它定性，resume 收口或重派 |
| 额度耗尽 | 无 `LAST.md`，`RUN.log` 尾部 `ERROR: You've hit your usage limit … try again at HH:MM`，exit 1 | 到点续接：有进度 resume，零进度重跑；不算轮次，不升档 |
| 崩溃 | 无 `LAST.md`，日志无错误、停在半途 | 多为外层组杀，resume 或重跑 |

- 别在 `RUN.log` 里 grep 标记：Codex 开跑会回显简报原文，标记字样会在日志开头命中。
- 日志里反复对同一 pid `kill -0` / `ps` 且 git 零 commit，是自我监控死锁，立即杀掉重派。
- 进程活着、日志静默超过 20 分钟按卡死处理；`codex exec` 是单轮进程，BLOCKED 后必然退出，不会停着等。
- Codex 施工期间不在同一工作树跑门禁、切分支或改文件。

## 验收

对照简报验收，不只看「跑通了没有」：

- **交付**：简报里可验证的行为，主代理亲自跑关键门禁和场景，以实际结果为准。
- **重点**：用户最在意的那一两件是否真的做到，有没有被次要工作挤掉。
- **质量与品味**：读 diff。拒收简报外的新机制、兼容层、镜像实现的测试，以及读起来不像这个仓库的代码。问自己：这份交付配得上简报里写的门槛吗？
- 不过就写具体反馈：问题已定位，resume 修复；方向错了，改简报重派。

## 批次

- 一批是一个可独立验收的工作包，验收通过才放行下一批。
- 同一工作树内串行；并行只用各自独立的 worktree，且文件集不相交。
- 大工程常见切法：骨架（含 RED 测试）→ 重改动 → 收尾，各批按档位一节定档。

## 改-审循环

**审查**用全新会话保独立性，简报同样按五段写：背景讲清这批做了什么、为什么；交付是问题清单（严重度、位置、复现方式）；重点写最该挖的风险；质量与资源写清只报有把握的问题还是尽量覆盖；结尾写明只审不改，结论走 `-o`。可以换模型或换 agent 交叉审。审查从 `high` 起，触及不可逆资产的最终态对抗审用 `xhigh`。

**修复轮**续上原施工会话的上下文：

```bash
codex exec resume <session-id> -m gpt-6-astra -c model_reasoning_effort="<medium|high|xhigh>" \
  --dangerously-bypass-approvals-and-sandbox -o LAST2.md "<裁决或修复要求>"
```

- 用显式 session id，不用 `--last`：`--last` 只在当前 cwd 找，找不到会静默新开空会话（exit 0、无警告）。session id 跨 cwd 有效。
- effort 和权限旗标每次重传，resume 不继承，漏传会静默掉回 config 默认。
- resume 后核对日志头部 `session id:` 与原会话一致。
- 长修复轮同样按启动一节后台起。续接一律用裸 CLI，`/codex:*` 插件看不见裸调起的会话。
- 修复轮定档：问题已定位用 `medium`，审查指出的是设计问题用 `high`。
- 默认单路：首轮审查无阻断即收口；有阻断就修复后换新会话复审，一轮干净即可。触及不可逆资产或反复冒出新阻断，才审到连续两轮无新发现。
- **熔断**：阻断性修复超过 3 轮不收敛，或修 A 破 B 来回振荡，就停下回方案层重写简报，不加轮次。
