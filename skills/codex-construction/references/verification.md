# 独立验证

主代理验收之外，再让没写代码的全新会话把改动跑一遍。作者只会检查自己想做的东西，独立验证的价值在于换一方按用户的方式去用它、设法让它违背意图。读 diff 写意见不在其中：这类意见每一轮都能再挑出一批，照着改只会往代码里堆防御和抽象。

## 起一个验证会话

用全新会话，按 SKILL.md 启动一节起（档位参考 `high`），不带施工上下文。验证简报写清：

- 这批做了什么、为什么、用户最在意什么；
- 要守的行为和数据；
- 怎么驱动：项目的 verify skill 和要走的功能、命令、数据集；
- 最该挖的风险。

红线照写，结尾不用施工的运行约定，照抄下面这段：

```text
这是无人值守的单轮会话，没有人会回答问题。你的任务是验证不是施工：像用户一样把这批改动跑起来，设法让它违背上面写的意图。
每个发现都要有一次运行作证：确切命令、实际输出、按意图应有的输出。复现脚本和临时数据放在工作树之外，不改工作树、不 commit；结束前拆掉自己起的进程和登记的 worktree，脚本和输出留着作证。
没跑过的不报：风格、命名、结构，以及要等将来再改才会成立的风险，都不在本次范围。没有发现是正常结果。
最终消息先列每项交付的验证结果（命令与关键输出），再列发现（标题 / 命令 / 实际输出 / 应有输出 / 违背哪条意图），没有就写「无」。末尾单独一行 `VERIFY DONE`。
```

可以换模型或换 agent 交叉验证，不同模型撞到的失败不同。

## 裁定

主代理逐条重跑发现里的命令，输出确实显示失败、且失败违背意图的才成立，同根因的合并。成立的发现里，用户会碰到的 bug、失败的门禁、改动写错的文档进修复轮（按 SKILL.md 的续接与验收两节），其余写进后续建议。基线（主干或前序批次）本来就有的问题，这批没有复制它、也没有新走到它，就不算这批的。

## 什么时候再验一次

完整的独立验证一批做一次。修复轮之后，主代理重跑那几条失败的命令就够了；修复引入了新行为、重新设计或大 diff 时才再做一次完整验证。对同一份代码反复挑，每一轮都能再挑出一批，收不了口。
