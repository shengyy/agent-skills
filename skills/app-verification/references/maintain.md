# 维护 verify skill

应用一变，功能地图就开始腐烂。这一轮让 verify skill 和地图重新说真话。严格的单位是功能，不是每一句话：每个功能文件都从源码过一遍，每个功能都实际驱动一次，不必把每条要点都跑成命令。

## 结局

只取其一，并说明是哪一个：

- **clean**：每个功能都有源码与实测覆盖，没有要改的。不开分支、不提交。
- **changed**：一个变更，只含已证明的文档、驱动脚本或地图修正。
- **blocked**：覆盖没能完成，或已证明的修正没法安全交付。写清卡在哪。

## 改动范围

只改 verify skill 自己的目录（SKILL.md、`features/`、它拥有的驱动脚本）。不改产品代码：地图描述的行为应用已经不做了，要么是文档漂移（改地图），要么是产品回归（报告给用户，别在文档里掩盖）。

## 一轮维护

1. **找到目标**：带启动、驱动各节和功能地图的项目 skill。多个候选就问用户；一个都没有，就停下改走 SKILL.md 的创建流程，不要凭空造一个目标。
2. **索引卫生**：读地图索引并列出同级文件，修掉缺失、多余、重复和死链。
3. **源码过一遍**：工具支持时，每个功能文件派一个只读子代理并行去读，各自从源码解释这个功能怎么工作，指出带引用的疑似漂移，给一条实测配方。子代理不驱动应用、不改文件。
4. **合并**：确认每个功能都有回报。把重叠的配方合并到尽量少的应用状态里。抽查被指出的漂移，干净的说法不必重证。扫一遍最近的改动，找地图里缺的用户可见表面——认定缺失要有具体的源码路径。
5. **实测**：源码看着干净也必须跑。由协调者一个人驱动，按 skill 自己的启动模型（常驻实例串行驱动，或短命 CLI 每次一个隔离会话）。每个功能至少驱动一次，不管遇到什么失败，全程守住三件事：
   - 实例出过意外，先体检再驱动：第一次驱动前、每个新会话、每次驱动失败后都体检。体检看不到的故障（进程健康但界面卡死）就重置到已知状态或重启，别指望它自己好。
   - 已经留下的证据熬过每一次清理，到写明的位置去核实，不靠假设。
   - 驱动起的东西不比它有用的时间活得久：失败尝试的残留，不管会话是卡住、退出还是共享的，都要清掉（共享实例清残留，不清实例）。

   体检失败是因为 skill 漂移，就在改动范围内修好、只重启被修改影响的部分、重试一次，还不行才判 blocked。走不到的功能，写明具体前提（鉴权、授权、操作系统、外部状态）和试过的路线，才能记为「已核实不可达」；地图漏写了这个前提，就是漂移。分诊里改过的驱动脚本，交付前要再实际驱动一次。最后一次驱动（含这些复证）之后统一拆除，证据留下。
6. **分诊**：用户视角的描述错了或缺了，是文档漂移，修。行为正常但驱动不了，是驱动缺口，修（脚本可执行、调用方式写进正文）。应用确实坏了，是产品缺口，记给用户，不进这次的变更。
7. **交付或停下**：changed 就交一个只含已证明修正的变更，交付前重读每个改过的文件；clean 或 blocked 不交变更，如实报告结局和覆盖情况。

运行笔记（覆盖了哪些功能、不可达的前提、确认的漂移、结局）记在临时位置，不提交。
